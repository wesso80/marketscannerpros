EXISTING PROTECTIONS TO PRESERVE
- middleware.ts:167 protects /api/admin before route handlers; admin pages redirect unauthenticated visitors. Most handlers independently call requireAdmin.
- lib/adminAuth.ts uses signed admin sessions, timing-safe secret comparisons and HttpOnly/SameSite cookies. Admin sessions have a 12-hour lifetime.
- The two routes lacking the inventory's common auth markers are explained: claude/growth re-exports the guarded growth handler; crypto-markets/summary validates a dedicated CRYPTO_SUMMARY_KEY and is the narrow middleware bot exception. They are not unguarded routes on this evidence.
- lib/publicDesign.ts:24 excludes /admin, /operator and /v2 from public design routing. Keep that exclusion.
- discoveryOnly.ts, adminEquities.ts and cryptoMarketsPause.ts separate admin pauses from shared public ingestion. Crypto entry/spend pause and simulated-exit pause are distinct switches.
- Paper account reads/writes commonly constrain workspace and portfolio IDs, use transactions/row locks, and expose reconciliation and simulated labels. Portfolio reset archives prior ledgers and validates the current portfolio ID, rather than deleting personal holdings.
- cryptoAutomation.ts uses an NX/TTL reservation and token-checked release; paper cycle/accounting tests cover additional coordination. Do not replace these with an unguarded UI-triggered loop.
- Global API response headers already prohibit caching; specific private responses add private/no-store. Redis admin prefixes and workspace-scoped ledger queries serve different purposes and must remain distinct.
- scoring.ts defines three independent scoring layers. A high personal-exposure flag must not suppress an otherwise valid research opportunity.

FINDINGS / PRIORITY
A1 — P1: Authentication decisions differ across entry layers (confirmed code discrepancy; production incidence unknown).
Evidence: middleware.ts:90 admits a signed is_admin claim or email/CID list. lib/adminAuth.ts:107 additionally uses isOperator with workspace matching. middleware.ts:277 refreshes ms_auth without retaining is_admin. app/api/auth/login/route.ts issues is_admin on Stripe-customer-ID sessions as well as email-prefixed sessions.
Consequence: an administrator with a cus_* identity can lose the middleware admission claim after a refresh on a public page, even though the route helper can still recognise the workspace. Separately, AdminClientLayout advertises secret-based verification, but middleware rejects a cookie-free /api/admin/verify request before its secret-checking handler. This legacy path should be clarified, not fixed by broadly allowing secret headers everywhere.
Tests currently cover helper acceptance and route source wiring, not the full middleware -> route -> refresh lifecycle.
Proposal: a dedicated admin authentication contract and cross-layer tests. Decide whether the legacy secret login is supported or retired. Do NOT edit public login/refresh code under the present admin-only authorization; any shared-auth change needs its own scope review and public regression checks.
Acceptance: signed-out/non-admin refused; approved admin session accepted; valid administrative app identity behaves consistently through refresh; invalid bot/header credentials cannot bypass middleware; public sign-in/tier outcomes unchanged.

A2 — P1 boundary constraint: Admin business and worker operations can change public behavior (confirmed dependency, not a newly discovered exploit).
Evidence: app/api/admin/trials/route.ts updates user_subscriptions; admin kill-switch uses lib/universe/personalUniverse; worker/ingest-data.ts and lib/worker/schedule.ts combine public ingestion, user jobs and admin jobs. Public CoinGecko webhook imports admin new-listing helpers.
Proposal: classify all proposed edits as private presentation, private research, or shared/public-effecting before implementation. Keep business writes, public entitlement storage, provider governors, shared cron jobs and schema changes out of this workstream.
Acceptance: public files unchanged; any shared-helper diff separately approved; no provider budget or worker schedule changes; no public response/entitlement/cache changes.

A3 — P2: Reading the crypto paper account can perform schema setup (confirmed).
Evidence: app/api/admin/crypto-markets/paper/route.ts:12 -> cryptoPaperState at lib/admin/cryptoPaper.ts:154 -> ensureExcursionTables and ensureSignalLedger. cryptoSignalLedger.ts:21/45 contains CREATE TABLE IF NOT EXISTS and executes the DDL statements. Errors are swallowed for optional sections.
Consequence: a supposedly read-only dashboard view can require DDL rights, add cold-start database work, and hide a missing-schema condition behind absent sections. No production call was made to reproduce this.
Proposal: move setup to explicit migrations in a separately authorised database task; have reads report readiness without DDL. Until then, do not use live paper-account GETs as a guaranteed read-only audit mechanism.
Acceptance: GET executes no CREATE/ALTER/UPDATE; missing tables return a clear readiness state; existing ledger read/accounting behavior unchanged; migration tested only on an isolated database first.

A4 — P2: Mutation protection and scope presentation are inconsistent (confirmed examples, not a claim all routes are vulnerable).
Evidence: portfolio-lab/reset/route.ts:8 checks origin, current portfolio ID, simulated mode, row lock and private headers. crypto-markets/paper/route.ts:21 has no corresponding origin call and exposes both workspace paper actions and global automation actions. cryptoAutomation.ts:9/14 writes one global Redis automation key, not a workspace-specific setting.
Consequence: an operator can reasonably confuse account-specific controls with a platform-wide toggle; the different route contracts are harder to audit. Existing session cookies and middleware remain protections; no cross-site exploit was demonstrated.
Proposal: explicit global-versus-workspace labels, actor/reason audit events and a standard admin mutation wrapper where appropriate. Keep existing lock/idempotency behavior.
Acceptance: action scope shown before mutation; denied action causes no provider/SQL work; cross-origin policy tested; repeated destructive request does not duplicate effects; public accounts untouched.

A5 — P2: Admin error responses can expose internal exception text.
Evidence: app/api/admin/kill-switch/route.ts:22/38 returns e.message/String(e) to the browser. Authentication still applies, so this is not evidence of anonymous exposure. Other handlers already return generic errors.
Proposal: admin-only generic error responses with server correlation IDs; retain diagnostics in controlled logs.
Acceptance: injected DB/provider error strings never appear in browser JSON; logs permit diagnosis without secrets; status and fail-closed behavior preserved.

A6 — P2: Settings is a placeholder, and navigation has competing definitions.
Evidence: app/admin/settings/page.tsx:6 renders explanatory cards without working controls. app/admin/admin-client-layout.tsx:70 defines the active extensive navigation; components/admin/layout/AdminShell.tsx and AdminSidebar.tsx define another shell/menu. Static search found no consumer of that alternate AdminShell. Discovery mode already hides many inactive destinations.
Proposal: improve the active admin shell only; label unavailable features honestly. Do not build controls that change public credentials or billing as a cosmetic settings task. Confirm alternate-shell reachability before removal.
Acceptance: one deliberate navigation source, working paths only, explicit active/paused state, no unimplemented settings promise; no public layout edits.

A7 — P2: Status needs to explain the combination of pauses, data age and job outcome.
Evidence: 66/81 pages pause under the default discovery-only rule, while admin equity pause, crypto spend pause, crypto exit pause, CoinGecko enablement and automation each have separate controls. Scheduler already distinguishes skipped from failed outcomes.
Proposal: an admin-only status overview showing effective state, reason, last successful observation/run, source and next expected run. Display stored telemetry instead of adding polling that spends provider quota.
Acceptance: intentionally skipped jobs never look failed or healthy-but-running; missing data never becomes zero; UI remains useful when Redis/provider services fail; no flag is toggled by viewing the page.
